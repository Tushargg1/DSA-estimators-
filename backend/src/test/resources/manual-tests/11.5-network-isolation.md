# Manual Test 11.5 - Network-failure isolation during polling

**Requirements:** 2.4, 9.1
**Task:** 11.5 (manual)

## Goal

Verify that when one platform's network/scrape fails mid-poll, the polling cycle
still processes every other platform and every other user normally - one platform
going down must never abort the whole cycle.

## Automated coverage (already in place)

This manual procedure is the primary check, but automated tests already pin the
same behaviour and run under `mvnw clean verify`:

- `PollingServiceTest.oneFailingPlatformDoesNotAbortTheRestOfTheCycle` (task 5.6)
  - a GFG `ScrapeException` mid-cycle does not stop LeetCode/Codeforces polling
  for any user, and no exception escapes `pollAllUsers()`.
- `PollingServiceTest.gfgParseFailureIsRecordedAsGfgParseFailure` (task 5.7) - a
  GFG parse failure is logged as an explicit `GFG_PARSE_FAILURE` event and
  recorded in `poll_status` (`last_failure_at` + `last_failure_reason`) without
  crashing the cycle.
- `CountingPipelineIntegrationTest.oneFailingPlatformDoesNotBlockOthersEndToEnd`
  (task 11.5, automated complement) - drives the REAL end-to-end pipeline
  (`pollAllUsers` -> `pollUserPlatform` -> persistence): with GFG failing for
  both users, each user's LeetCode solve is still persisted, counted, and rolled
  into `daily_counts`; `poll_status` records a GFG failure and a LeetCode success.

The steps below verify the same guarantee against a real running instance with a
genuine network interruption (which cannot be reproduced in a unit test).

## Preconditions

1. Backend running against a real Postgres (`mvnw spring-boot:run` or the
   packaged jar) with the 5-minute polling job enabled.
2. At least two onboarded users, each linking **at least two** platforms - e.g.
   both LeetCode and GFG (`onboarding_complete = true`).
3. Access to the application logs and the database (or the status/leaderboard
   endpoints) to observe results.

## Procedure

1. Confirm a healthy baseline: watch one or two normal 5-minute poll cycles.
   Every linked platform for every user should be fetched, and
   `poll_status.last_success_at` should advance for each platform.
2. Disconnect the network path to **one** platform only, so its adapter fails
   while the others still reach their APIs. Any one of:
   - Add a hosts-file entry that blackholes the platform host (e.g. point
     `leetcode.com` or the GFG profile host to `127.0.0.1`), or
   - Block outbound traffic to that host with a local firewall rule, or
   - Temporarily set an invalid proxy for just that host.
   Do this a few seconds before (or during) a poll cycle so a fetch is in flight
   when connectivity drops.
3. Let the next full poll cycle run.

## Expected results

- **(a) Failure is logged with platform + user + timestamp.** The logs show a
  handled failure for the disconnected platform (a scrape/timeout message, or a
  `GFG_PARSE_FAILURE` line for GFG), including the platform, the user id, and the
  timestamp - not an uncaught stack trace aborting the run.
- **(b) `poll_status` records the failure.** For the disconnected platform,
  `poll_status.last_failure_at` and `poll_status.last_failure_reason` are updated
  (visible via `GET /api/status/poll`).
- **(c) Other platforms/users still process.** For every other platform and every
  other user, polling proceeds normally - new solves are ingested, `daily_counts`
  updates, and `poll_status.last_success_at` advances.
- **(d) No exception aborts the scheduled job.** The cycle completes without
  crashing and the scheduler keeps ticking every 5 minutes (no stuck/aborted
  cycle). No submissions are lost for the healthy platforms, and no
  partial/rolled-back state is left behind (the disconnected platform simply has
  no new rows this cycle).

## Teardown

1. Restore network connectivity (remove the hosts entry / firewall rule / proxy).
2. Confirm the next poll cycle successfully polls the previously-disconnected
   platform again and stamps a fresh `last_success_at`, showing the failure state
   self-heals.
